# 自动模型与单场足球分析的执行说明

适用框架：v1.6，继承 v1.5 修订批次5并保留A01。日期：2026-09-22。

## 你需要做什么

平时直接给比赛双方；日期有歧义时补充比赛日期。有你准备采用的赔率截图就一起提供；没有截图，由分析者查可核实报价。你不需要每天手动训练，也不需要每场上传模型文件。仓库连接如到期，只在身份验证界面恢复授权，不在聊天发送密钥。

日程已经由用户确认开启。现有工作流每天 UTC 01:17（北京时间09:17）尝试更新数据、按需拟合、生成未来7天预测并保存状态；是否实际成功，以相应 Actions 记录和该联赛索引为准。接入工作不修改日程、算法或参数。

## 两个自动化环节

|环节|执行者和触发|实际产物|
|---|---|---|
|后台更新|原 GitHub Actions 每日运行；也可按原入口手动补更|原有模型、预测、验证/运行记录，并自动维护接入索引|
|单场分析|用户在聊天里要求分析某场比赛时，由分析者主动读取|带真实来源的单场模型包、最新基本面核查、具体盘口计算和框架报告|

每日调度不会把全部结果主动推送进每段聊天。固定仓库入口、逐联赛索引及本项目的读取规则连接这两个环节。读取并核验已有合法预测可以复用；重新训练不是每次分析的前提。

## 固定入口与文件

私人仓库：[wuyan0231-hub/football-model](https://github.com/wuyan0231-hub/football-model)。程序与规则在 `main`，运行状态在 `model-state`。分析者先查看最近相关Actions的执行和保存状态，再解析最新状态提交 SHA，用该 SHA 读取同一版本的文件，防止一次分析混用更新前后的状态。若最新任务在写入状态之前失败，旧索引不会知道该次失败；必须把此缺口单列，不能把旧索引当成本次更新成功的证明。

|位置|用途|
|---|---|
|`model-state:runtime/integration/index.json`|机器可读总索引：逐联赛最近尝试、模型、预测位置及失败/无比赛等状态|
|`model-state:runtime/integration/index.md`|便于查看的状态摘要|
|`model-state:runtime/models/<league>.json`|模型ID、真实参数、训练时间、覆盖与验证摘要|
|`model-state:runtime/predictions/<run_id>/<league>.json`|真实比赛ID、主客队ID、时间、完整比分分布与胜平负|
|`model-state:runtime/validation/<league>/<run_id>.json`|该次固定时间留出验证及逐场预测；模型包内亦有验证摘要|
|`model-state:runtime/reports/history/<run_id>.json`|该次运行与来源代码版本；不会因单场分析改写|
|`model-state:runtime/match_calls/`|接入联通检查或后续已保存的单场读取记录；不等于已完成当场基本面分析|
|`main:AGENTS.md`|面向分析助手的固定接入规则|
|`main:docs/football-framework-v1.6.md`|完整框架副本|

`runtime/reports/latest.json` 只代表最后一次任务，可能只训练了韩国K1，不能据它认定其他联赛没有模型。索引从各次记录归集各联赛状态；不会给旧训练时间换上新的日期。

## 每场怎样执行

1. **确认对象。** 查明赛事、比赛ID、主客队ID、开赛时刻、当前未开赛状态及场地。展示北京时间，同时保留原时区时间。双方队名相似时不得猜测。
2. **取得模型。** 读取固定状态提交的索引和对应模型/预测；核对模型版本、训练截止、数据观测时间、预测生成时间、最新该联赛运行状态。模型现有最长14天限制和新球队不支持规则保持不变。
3. **生成单场包。** 读取保存的预测，调用原 `score_distribution()` 复算并核对原概率，不调用训练函数。记录状态提交、文件路径、文件哈希、模型和比赛身份、验证摘要。已开赛、前视时间、错联赛/错队、陈旧模型或输出不一致时拒绝数值接入。
   欧国联预测若带 `registry_snapshot`，须从同一固定状态提交取得其指向的 `runtime/registries/nations_venues/<摘要>.json`，交给原单场命令核验。自动登记流程见欧国联接入说明；不得只拿种子表或最新表替代预测当时的场地证据。
4. **补本场资料。** 自行核查当前赛程是否改期/取消、是否中立场、伤停、预计首发、战术、轮换与赛程背景。当前接入程序不联网核查这些项目，所以包内仍会列待核项；不能将“包生成成功”写成“全部事实已核实”。
5. **核赔率并实际计算。** 用户截图按读取规范v1.1处理；没有截图则查有来源/时间的有效报价。用合法比分矩阵按框架§10、§11、§22汇总具体市场结算，包含四分之一盘五态。只有真实报价与实际计算都具备时才填点估计EV；概率是探索性估计，赔率比较与已确认价值分开。
6. **三市场选主方向。** 先比较市场内部两侧/三项，再跨市场比较，给唯一相对方向及单腿串关适配。历史攻防进入模型；伤停等未量化因素以有依据的条件情景处理，不随意给概率加减分。
7. **保留记录。** 报告注明框架版本、模型ID、训练截止、实际读取/复算的预测记录、报价截点、未覆盖因素和主要反证。复盘锁定原结论，不用后来模型覆盖原预测。

报告的最小接入说明为：

> 本场按框架v1.6执行，继承v1.5修订批次5。已读取〔状态提交、预测记录〕；模型〔真实ID〕，训练截止〔时间〕，读取/复算时间〔时间〕。历史攻防为模型量化；临时阵容及其他未建模因素为定性或未加权条件情景。模型仍为探索性固定留出基线。

方括号内容必须来自当次真实操作；没有读取时明确写未读取，不照抄示例。

## 操作命令（分析者使用，用户不需要输入）

以下命令从项目根目录执行，输入是已经授权取得的真实 `runtime` 状态文件。

```bash
python -m football_model.integration index --runtime runtime --config config.json
python -m football_model.integration match --runtime runtime --config config.json --league mls --match-id 1490209 --state-commit STATE_COMMIT --output runtime/match_calls/example.json
```

`STATE_COMMIT` 必须替换为实际读取的状态提交。1490209只是本次联通检查采用的真实已存赛程ID；分析其他比赛必须改为实际ID。默认分析截点是执行时的UTC时间；可用 `--as-of` 指定带时区的明确截点，禁止借它进行使用未来数据的历史回算。程序不获取赔率，不修改球员影响，也不生成下注操作。

索引生成由原 `run_pipeline` 末尾自动执行，因此后续每日任务会一并保存索引。单场读取包不是新训练结果；若未来需要把当次聊天记录另存云端，可将该包随实际分析记录保存，不能声称后台已自动保存未上传的聊天记录。

## 遇到缺口怎样继续

|情况|处理|
|---|---|
|有完整且可适用的已存预测|读取、复算核验后使用；仍补查本场资料|
|未来7天预测为0场|如实标无预测；先核对真实赛程和日期，不把0场当零概率|
|比赛找不到或预测窗口外|先核比赛身份及最新赛程；必要时按原工作流补更，未生成对应输出前不填模型概率|
|最新更新失败或模型陈旧|显示失败/陈旧原因，不把历史成功当作本次成功；可继续定性分析|
|新球队尚不支持|按用户已决定的范围暂缓冷启动；不补默认概率|
|欧冠|国内模型不能直接拼接，继续定性分析|
|场地、开赛时间发生变化|旧包不能直接应用，重新核对并用适用模型/输入重算；不把名义主客模型当中立场已修正|
|关键伤停未进入模型|保留基础概率的真实含义，按A01做情景；不声称已完成数值阵容修正|
|仓库暂不可读|明确实际未读取模型，继续可完成的定性分析；只有认证确实阻断时才请求恢复连接|

## 本次接入不代表哪些能力升级

现有模型是15个国内联赛及欧国联分别拟合的时间衰减正则化攻防泊松基线；不含已训练的Dixon–Coles修正、xG、球员或滚球模块。验证保持固定时间留出，不能改称滚动验证。完整比分矩阵使盘口数学映射可计算，但深盘、大小球和实际收益尚未完成专项验收。美职联、墨西超初步验证仍落后于简单联赛基准；其余联赛的探索性评分也不等于盈利证明。

完整的A01、三市场比较、反证、结算与复盘政策继续沿用v1.5修订批次5。v1.6主要补齐真实模型状态与每场读取流程。
