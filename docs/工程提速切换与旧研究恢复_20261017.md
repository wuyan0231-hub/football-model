## 恢复原研究的具体入口

恢复前先结束本次维护、确认共享写入队列没有维护任务、保留当前固定状态提交，并核下面的条件。暂停期间不自动执行本节命令。

1. 核原 Actions 运行的 `head_sha` 为上表旧源码、原 `head_branch` 为 `main`、输入仍为原 `research_only` 和原联赛范围，且原运行已终止。保存原失败、取消和跳过状态。
2. 使用**原运行的 Re-run failed jobs**，不要从最新 main 重新派发 `research_only`。例如原运行号为 `38928003279` 时，恢复命令为 `gh run rerun 38928003279 --failed --repo wuyan0231-hub/football-model`。这是供审阅的入口，本文件不会执行或调度它。
3. 重跑后核实际运行仍使用原源码、原 main ref 和旧 50 文件指纹。原 checked-save 入口要求源码 HEAD、`GITHUB_SHA`、main ref 和加载标记一致；本次不放宽此要求，也不伪造这些字段。
4. 从当时最新状态恢复后，逐联赛让原生检查点核输入、协议、实现、成熟目标、新鲜度和固定持久闭包。已完成的结果核通过则复用，不重复拟合。资料变化导致失配时如实保留，先报告范围；不得直接升级成全部联赛重跑。
5. 原运行已有通过的联赛作业不重跑；取消或跳过的剩余作业继续按旧队列串行写入。全 19 联赛核验和原最终短轮仍由原实现完成，原研究产物不改写成新实现产物。

如果平台不支持原运行按失败项恢复，停止在该边界，另审查固定旧源码入口；不能以新 main 重算全部联赛代替恢复，也不能改守卫绕过来源验证。

## 2026-10-18 固定冷读失败与最小缓存准入修补

原新实现 `b49e96b3…` 的无预热固定诊断运行 `39082219909` 实际到达 1500 秒截止；清理及最终核验后记录 1511.532 秒，状态为 `diagnostic_deadline`。完整冻结未证明通过，原失败保留，不用以前带预热的 17 分 45 秒结果替代这条生产冷读路径。

后续纯观测前段已区分具体原因：单个读取进程正常复用、没有缺件返回；3 个固定来源 manifest 原字节共 135,342,008 B，最大 58,189,975 B，与压缩传输原件竞争同一 64 MiB 字节 LRU。在约 2539 次观察调用时，manifest 已读取 10 次、返回约 484 MB；2528 次完成的 transport 读取只对应 1723 个不同对象、合计 4,239,092 B，但实际命中仅 1 次。多次读取的传输对象虽可容纳，仍被大型 manifest 挤出。这些是有界前段证据，不能替代完整闭包耗时验收。

本修补仅让精确路径 `state_storage.json` 不进入字节 LRU；64 MiB 上限、其他传输对象缓存、原 manifest 解析与校验缓存上限均不变。不增加负缓存、磁盘缓存、预热或新资源上限；每条冷引用仍执行固定 manifest 比对、compressed SHA、解压、raw SHA 及原 JSON／秘密信息检查。原始返回字节和缺失／损坏错误保持；真实 Git 回归另外核验重复冷引用仍逐次完成 manifest 检查和解压。

诊断中 `original` 明确表示之前的“全部 blob 准入”基线，`skip_manifest` 表示本修补策略。新 native 的重放一致性核 `actual_vs_skip_manifest_hit_mismatches`，不把 `actual_vs_original_hit_mismatches` 为零作为新实现门禁。两种重放仅比较同一有界请求前段的缓存行为；追踪达到上限即标不完整，不能由命中差直接推算耗时提升。

分钟日志拆为短行：全局摘要少于 400 字符、每类少于 350、每读取器少于 800；完整结构仍保存在原诊断 checkpoint 和最终 artifact。新指纹、窗口守卫与工作流执行参数同步为上表 `41cb9acb…`；固定输入、1500 秒、无预热及全部原验收门保持。须等新的完整固定闭包及保存回读真实通过，才能报告相应工程验收完成。
